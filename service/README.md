# 제스처 서비스 — CLI와 Windows GUI

기존 CLI는 카메라 → MediaPipe → 시간 기반 시퀀스 버퍼 → 기존 전처리 → LSTM → 중복 방지 → **실행 예정 명령 로그**를 연결합니다. CLI의 DRY RUN 동작은 유지합니다. 새 Windows GUI에는 실제 단축키 전송을 별도 계층으로 추가했습니다. YOLO, 학습, 튜닝, 실행 중 모델 교체, exe 생성은 이번 GUI 범위에도 포함되지 않습니다.

## 새 Windows GUI

GUI의 실행·설정·수동 검증·제한 사항은 [GUI_README.md](GUI_README.md)를 확인하세요. 아래의 기존 `service.main` 설명과 S/X/Esc 조작은 **CLI 전용**입니다. GUI는 `service.gui`로 실행하고 전역 `Ctrl+Alt+G`로 인식을 시작/중지합니다.

최초 구현 시에는 PySide6가 없어 GUI 테스트를 건너뛰었습니다. 이후 사용자 설치 후 모의 트레이 구성, 기본 모델 선택 및 오른손 전용 정책을 검증했습니다. 실제 카메라·전역 키 전송·Windows 초점 유지는 여전히 수동 확인이 필요합니다. 아직 설치하지 않은 환경의 설치 명령은 다음과 같습니다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r .\service\requirements-gui.txt
.\.venv\Scripts\python.exe -m service.gui --device auto
```

GUI 기본 모델은 `artifacts/four_class_lstm_1layers_001/best_model.pt`(오른손 4클래스)입니다. 우선순위는 `--checkpoint` 지정 → 저장된 사용자 모델 경로 → 기본 모델입니다. 기본 경로는 실행 위치가 아니라 저장소 위치를 기준으로 찾습니다. 기본 모델로 돌아가려면 설정의 모델 경로를 비워 저장하고 `--checkpoint` 없이 재시작하세요.

GUI는 OFF로 시작하며 사용자가 인식을 시작하면 **실제 활성 앱에 키를 전송**합니다. 먼저 저장할 필요 없는 테스트 문서/무해한 창에서 사용하세요. 설치 후 GUI 모의 테스트를 먼저 실행하는 방법은 새 안내에 포함했습니다.

## 실행

서비스는 오른손 4클래스 모델을 지원하며 기존 오른손 3클래스 모델도 호환합니다.

| 클래스 | 지원하는 손과 동작 |
| --- | --- |
| swipe_left (0) | Right, 화면 왼쪽 이동 |
| make_fist (1) | Right, 손 펴기 → 주먹 쥐기 |
| no_gesture (2) | Right, 정지·일상 비명령 동작 |
| finger_snap (3) | Right, 손가락 튕기기 |

MediaPipe가 Left로 판정한 프레임은 분류 입력에서 제외하고 기존 시퀀스를 초기화합니다. 오른손으로 돌아오면 새 구간과 중립 확인이 필요합니다. 검출 자체를 오른손으로 한정하는 기능은 아니며, 손 구분의 오판정 가능성은 남습니다.

좌우 반전 증강과 왼손 모델은 지원하지 않습니다. finger_snap은 새 오른손 4클래스 체크포인트에서만 활성화됩니다. 기본 모델 경로는 기존 3클래스 모델이므로, 네 클래스를 사용하려면 새 학습 결과를 명시적으로 선택하세요. GUI와 기존 전역 단축키·알림·미리보기 기능은 유지합니다.

프로젝트 루트 PowerShell에서 실행합니다. CLI는 `--checkpoint`가 필수이며, 아래는 현재 기본 4클래스 모델을 지정하는 예시입니다. 최종 성능 검증을 마친 선택이라는 뜻은 아닙니다.

```powershell
.\.venv\Scripts\python.exe -m service.main --checkpoint .\artifacts\four_class_lstm_1layers_001\best_model.pt --device auto
```

다른 학습 결과를 쓰려면 경로만 바꾸면 됩니다. 층 수와 hidden 크기는 저장된 설정으로 복원하므로 따로 지정하지 않습니다. `python service/main.py ...` 형태도 지원하지만 `-m service.main` 실행을 권장합니다.

카메라를 열지 않고 옵션만 확인하려면:

```powershell
.\.venv\Scripts\python.exe -m service.main --help
```

MediaPipe 자산은 기존 수집기와 같은 `models/hand_landmarker.task`를 사용합니다. 배포할 때 `service/`만 가져가지 말고 기존 `training/models.py`, `training/prepare_dataset.py`, `training/evaluate.py`, `training/train.py`와 프로젝트 의존성, MediaPipe 자산도 함께 유지하세요. 데이터셋이나 전처리 배열은 서비스 실행에 필요하지 않습니다.

## 조작

- 시작 상태는 **OFF**입니다. 카메라 미리보기는 보이지만 MediaPipe 처리, LSTM 추론, 명령 이벤트는 실행하지 않습니다.
- `S`: 인식 ON. 매 제스처마다 누르는 키가 아닙니다. ON 상태에서 다시 눌러도 버퍼를 초기화하지 않습니다.
- `X`: 인식 OFF. 버퍼, 후보/중립 횟수, cooldown, 마지막 예측과 이벤트 표시를 초기화합니다. 프로그램과 카메라는 유지됩니다.
- `Esc` 또는 카메라 창 닫기: 프로그램 종료 및 카메라/MediaPipe/창 해제.
- 터미널의 `Ctrl+C`도 자원을 해제하고 종료합니다.

**카메라 창에 포커스가 있어야 S/X/Esc를 받습니다.** 전역 단축키가 아니므로 다른 앱이 활성화되어 있으면 인식 ON/OFF 키를 받지 못할 수 있습니다. 단일 동기 루프라 추론 중 입력된 키는 다음 루프에서 처리됩니다.

실행 시에는 아래 로그만 출력합니다. 실제 앱 단축키는 아직 지정하지 않았습니다.

```text
[DRY RUN] gesture=swipe_left, action=SWIPE_LEFT_ACTION
[DRY RUN] gesture=make_fist, action=MAKE_FIST_ACTION
```

no_gesture, 손 미검출, 품질 불량, 낮은 확률의 결과에는 실행 로그를 출력하지 않습니다.

## 사용자 안내: 동작은 언제 확정되나요?

**손이 보이고 제스처를 했다고 즉시 명령이 실행되는 것은 아닙니다.** 현재 서비스는 최근 움직임을 반복해서 분류한 뒤, 같은 결과가 안정적으로 이어질 때 한 번 확정합니다. 아래 숫자는 CLI 옵션을 바꾸지 않은 기본값 기준입니다.

### 인식 알고리즘 순서

1. **새 입력 구간 확보:** S로 인식을 시작하거나 버퍼가 초기화되면 최근 구간을 모읍니다. 기본 WARMUP은 1.5초이며, 손 검출률·프레임 수 등 품질 조건도 통과해야 합니다.
2. **최근 움직임 분류:** 이후 약 0.15초 간격으로 최근 1.5초를 전처리하여 LSTM에 전달합니다. 현재 프레임 한 장만 보는 것이 아닙니다. 매 제스처마다 새로 1.5초를 기다리는 것도 아니며, 겹치는 최근 구간을 계속 평가합니다.
3. **후보 안정화:** 같은 명령 클래스가 0.8 이상의 softmax 점수로 3회 연속 나와야 확정됩니다. no_gesture는 실행할 명령이 아닙니다.
4. **한 번 실행:** 확정되면 `[DRY RUN]` 로그를 한 번 출력합니다. 현재 버전에서는 실제 단축키를 보내지 않습니다.
5. **다음 명령 준비:** 실행 후 최소 1초의 cooldown이 끝나고, 높은 점수의 no_gesture가 3회 연속 확인되어야 다음 명령을 받습니다. 두 조건은 동시에 충족되어야 하며 단순히 시간이 지났다고 재실행하지 않습니다.

예를 들어 이미 입력 구간이 확보되어 있고 실행 가능한 상태라면 다음처럼 진행됩니다. 아래 점수는 설명용 가상 값입니다.

```text
첫 유효 예측 시점       make_fist 0.91 → Candidate 1/3
약 0.15초 후            make_fist 0.94 → Candidate 2/3
다시 약 0.15초 후       make_fist 0.93 → 확정, DRY RUN 로그 1회
```

첫 유효 예측부터 세 번째 확인까지는 이상적으로 약 0.3초가 추가됩니다. 이는 동작 시작부터의 전체 지연이나 보장된 처리 시간이 아닙니다. 프레임 속도, 처리 시간, 품질 보류와 예측 변화에 따라 더 오래 걸릴 수 있습니다. 화면의 동일한 예측을 여러 번 표시한 것은 확인 횟수로 세지 않습니다.

### 왜 동작 후 손을 잠깐 유지해야 잘 인식될 수 있나요?

코드에 **“동작 후 반드시 정지해야 한다”는 조건은 없습니다.** 다만 다음 이유로 잠깐 유지하는 것이 확정에 유리할 수 있습니다.

- 동작 후에도 최근 1.5초 구간에는 이동하거나 주먹을 쥐었던 과정이 남습니다. 손을 유지하면 이 과정이 포함된 여러 구간을 연속 확인할 수 있습니다. 정지 프레임만으로 스와이프를 판단한다는 뜻은 아닙니다.
- 바로 다른 동작을 하면 예측 클래스가 달라지거나 점수가 낮아져 후보 횟수가 끊길 수 있습니다.
- **Candidate가 1/3 또는 2/3일 때 손을 화면 밖으로 빼면**, 미검출 처리로 후보 횟수가 초기화됩니다. 앞에서 한두 번 맞게 분류했더라도 명령은 확정되지 않습니다.

따라서 첫 버전을 사용할 때는 손을 화면 안에 둔 채 동작을 수행하고, 확정 로그를 확인한 뒤 중립 상태로 돌아와 다음 동작을 시도하세요. 오래 유지한다고 반드시 인식되는 것은 아닙니다. 시간이 지나면 실제 동작 구간이 버퍼에서 빠지므로 화면의 예측과 보류 이유를 함께 확인해야 합니다.

여기서 **중립 상태는 시스템이 no_gesture로 분류하는 구간**입니다. 손을 화면 밖으로 빼는 것은 중립으로 세지 않습니다. 0.75초 이상 연속 미검출되면 버퍼와 판정 상태가 초기화되고, 손을 다시 보여준 뒤 새 구간에서 중립을 확인해야 합니다. 따라서 매 명령마다 손을 뺐다 넣는 방식은 권장하지 않습니다.

### 화면으로 기다리는 이유 구분하기

| 화면 표시 | 의미와 확인할 내용 |
| --- | --- |
| WARMUP | 새 구간 확보 중입니다. 모델이 허용하는 손 하나를 화면에 유지하세요. |
| Candidate 1/3 또는 2/3 | 모델이 명령 후보를 냈지만 연속 확인이 아직 부족합니다. 손을 바로 빼면 초기화됩니다. |
| Low confidence | 예측 점수가 실행 기준보다 낮습니다. 단순히 후보 횟수만 기다리는 상태가 아닙니다. |
| No valid/allowed hand / Expected ... | 손 미검출, 불명확한 손 정보 또는 모델이 허용하지 않는 손입니다. 현재 예측과 연속 횟수가 초기화됩니다. |
| Quality hold | 구간의 프레임 수·검출률·결측 길이 등 품질 조건을 충족하지 못했습니다. 뒤에 표시되는 원인을 확인하세요. |
| COOLDOWN | 이전 실행 후 재실행 제한 시간입니다. 시간이 끝나도 중립 확인이 필요합니다. |
| WAIT NEUTRAL | 다음 명령을 받기 전에 no_gesture의 연속 확인을 기다립니다. 손 미검출은 확인 횟수에 포함되지 않습니다. |
| Event confirmed / DRY RUN 로그 | 명령이 확정되었습니다. 현재는 로그만 출력합니다. |

동작 직후 **Latest prediction은 이미 맞는데 Candidate만 증가한다면 판정 안정화에 따른 대기**일 가능성이 큽니다. 반대로 손을 유지한 뒤에야 예측 클래스 자체가 맞아진다면 입력 구간 구성이나 모델의 분류 특성도 살펴봐야 합니다. 두 상황을 구분하지 않고 모든 지연을 LSTM의 한계로 단정할 수는 없습니다. 실제 입력 로그 없이 특정 테스트의 원인을 확정할 수 없으며, 초기 설정은 실시간 검증 후 조정할 대상입니다.

## 파일별 역할

| 파일 | 역할 |
| --- | --- |
| main.py | 옵션 검사, 단일 카메라 루프, 키 입력, 화면 표시, 자원 해제 |
| hand_tracker.py | MediaPipe VIDEO 초기화, 모델이 허용하는 손의 원본 랜드마크·handedness 전달 |
| predictor.py | 체크포인트 한 번 복원, 전처리 호환성 검사, 기존 함수로 전처리 및 LSTM 추론 |
| gesture_controller.py | ON/OFF, 시간 버퍼, 추론 주기, 후보 안정화, cooldown 및 중립 복귀 |
| actions.py | 확정 이벤트를 명령 이름과 연결해 콘솔에 출력하는 경계 |
| policy.py | 모델 라벨 계약과 분리된 서비스 오른손/명령 허용 정책 |
| yolo_gate.py | 정적 손모양 3초 유지 판정과 YOLO 로딩. GUI 게이트 전용 |
| test_service.py | 실제 카메라와 학습 자료 없이 합성/모의 입력으로 검증 |

모듈 import만으로 카메라/MediaPipe detector나 체크포인트를 열거나 파일을 저장하지 않습니다. MediaPipe 의존성은 tracker 생성 시 불러옵니다. 실제 키 입력 전송 라이브러리는 사용하지 않습니다.

## 옵션과 시간 구간

| 옵션 | 기본값 / 허용 범위 |
| --- | --- |
| --checkpoint | 필수, train.py 형식 체크포인트 경로 |
| --camera-index | 0 / 0 이상의 정수 |
| --device | auto / auto, cpu, cuda |
| --window-seconds | 1.5 / 양수, 체크포인트 min_duration~max_duration 안 |
| --inference-interval | 0.15 / 양수, 초 |
| --confidence-threshold | 0.8 / 0~1 |
| --stable-predictions | 2 / 양의 정수 |
| --cooldown-seconds | 1.0 / 0 이상, 초 |
| --rearm-predictions | 2 / 양의 정수 |
| --reset-gap-seconds | 0.75 / 양수, 초 |

이 숫자는 실제 성능을 검증한 최적값이 아니라 초기 실험값입니다. auto는 CUDA가 가능하면 GPU, 아니면 CPU입니다. 사용할 수 없는 cuda를 명시하면 오류로 종료합니다. NaN/Inf 설정은 거부합니다.

`reset-gap-seconds`는 추가 안전 옵션입니다. 연속 미검출, 프레임 획득 간격의 큰 공백, 한 프레임 처리 지연에 적용해 과거 구간의 명령이 늦게 실행되는 것을 막습니다. 임계 시간 이상 걸린 프레임의 이벤트는 버리고 새 구간을 요구합니다. 장치가 느려 계속 초기화된다면 화면과 로그를 먼저 확인하세요. 이 기능이 실제 서비스 응답 시간을 보장하는 것은 아닙니다.

window-seconds는 **카메라에서 모으는 실제 시간 구간**입니다. seq_len은 이 구간을 리샘플링한 후 모델에 넣는 시점 수입니다. 1.5초 동안 원본 45프레임이 들어왔다고 해도 체크포인트 seq_len=32면 기존 전처리로 32개 시점에 맞춥니다. 원본을 무조건 32프레임 모으거나 고정 FPS를 가정하지 않습니다.

시작 직후에는 지정 시간만큼 새 구간을 모으는 WARMUP 상태입니다. 그 이후 최근 window-seconds 안의 프레임을 유지하고 추론 주기에 맞춰 새 평가를 수행합니다. 실제 프레임 경계 때문에 구간 길이는 지정값보다 조금 짧을 수 있습니다. min_duration 경계와 너무 가까운 window 또는 낮은 FPS에서는 품질 보류가 생길 수 있으며, 기준을 자동으로 완화하지 않습니다. 버퍼는 시간으로 제한하고 비정상적으로 10,000프레임을 넘으면 오류로 중지합니다.

짧은 미검출은 NaN 좌표와 detected=False를 남겨 시간축을 보존합니다. 현재 프레임이 미검출이면 추론하지 않고 예측/후보/중립 횟수를 지웁니다. 검출이 돌아오면 기존 quality 기준을 만족하는 구간만 보간하여 추론합니다. 긴 미검출 후에는 버퍼를 버리며 손이 다시 들어올 때 새 구간을 시작합니다.

## 전처리·체크포인트 계약

서비스는 체크포인트 하나를 시작 시 로딩합니다. `weights_only=True`, CPU map_location으로 읽고 저장된 model_config 및 strict state_dict 로딩으로 모델을 복원합니다. 공통 계약은 단방향 LSTM, input_size=66입니다. swipe_left=0/make_fist=1/no_gesture=2에 finger_snap=3을 추가한 num_classes=4 모델을 지원합니다. 기존 num_classes=3 모델도 해당 세 클래스에 한해 호환합니다. 라벨·출력 수·전처리 버전이 서로 맞지 않는 설정이나 비정상 가중치는 거부합니다.

전처리는 `training.prepare_dataset.preprocess_sequence()`를 그대로 사용합니다. 체크포인트의 seq_len과 quality를 적용하며 현재 `build_config()`가 설명하는 특징 수식·버전·결측 정책·반전·표준화 등과 일치해야 합니다. 참가자 배정 같은 학습용 메타데이터는 입력 특징으로 쓰지 않습니다. 새 전처리 방식의 모델을 배포하려면 서비스 호환성도 함께 검증해야 합니다.

손목 기준 상대 xyz 63개 + 첫 출력 프레임 대비 손목 누적 dx/dy 2개 + 상대 손 크기 1개를 기존 방식대로 생성합니다. 보간이나 정규화를 중복 적용하지 않으며 손목 이동량이 작다는 이유로 배제하지 않습니다. 정지 no_gesture도 정상 입력입니다.

모델은 eval/inference_mode로 실행하며 입력은 float32 `(1, seq_len, 66)`입니다. argmax로 클래스를 선택하고 softmax는 표시와 판정 점수로만 사용합니다. softmax 값은 실제 정답 확률을 보증하지 않습니다. 모델 가중치 갱신은 없으며 재시작 전까지 같은 모델을 사용합니다. 새 best_model.pt를 적용하려면 프로그램을 종료하고 교체한 뒤 재시작하세요. 학습 완료/성능 평가는 배포 전에 별도 evaluate 단계에서 확인해야 하며 서비스가 이를 대신하지 않습니다.

## 안정화·중복 방지 상태

1. OFF → ON 직후에는 첫 명령을 받을 수 있습니다. 단, 새 구간을 모으는 WARMUP은 거칩니다.
2. 확률 기준을 통과한 같은 명령 클래스가 stable-predictions회 연속 추론되면 한 번 확정합니다. 화면 프레임 수가 아닌 **새 추론 횟수**를 셉니다.
3. 클래스 변경은 후보 횟수를 새 클래스의 1부터 시작합니다. 낮은 확률/품질 부족/미검출은 후보와 중립 연속 횟수를 0으로 만듭니다.
4. 실행 후에는 모든 명령을 잠그고 cooldown에 들어갑니다. 같은 주먹이나 스와이프가 계속 예측되어도 시간이 지났다는 이유만으로 반복 실행하지 않습니다.
5. 충분한 확률의 no_gesture가 rearm-predictions회 연속 확인되고 cooldown도 끝난 새 중립 예측 시점에 다시 명령을 받습니다. cooldown 중 중립 횟수는 누적하지만 명령/낮은 확률/미검출이 끼면 중립 연속성이 끊깁니다.
6. 손 미검출은 no_gesture가 아닙니다. 긴 미검출·카메라 공백·과도한 처리 지연은 버퍼와 이전 표시를 초기화하고, **새 구간에서 중립을 확인한 뒤** 명령을 받습니다. 단순히 손을 뺐다 넣는 것을 중립 동작으로 세지 않습니다.
7. X 후 S는 사용자의 명시적인 새 인식 세션이므로 초기 상태로 돌아가 첫 명령을 받을 수 있습니다.

중립 상태 없이 연속으로 두 명령을 수행하면 두 번째 동작을 놓칠 수 있습니다. no_gesture 판정이 불안정하면 다음 명령을 받지 못할 수도 있습니다. 첫 버전의 보수적인 규칙이며 실시간 테스트 후 개선할 부분입니다.

## 화면과 수동 검증

화면은 기본 OpenCV 폰트 제약 때문에 영어로 표시합니다. OFF/WARMUP/ACTIVE, 손 상태, 버퍼 길이, 최신 예측과 확률/경과 시간(age), 후보 횟수, 실행 가능 여부, 중립 횟수, 마지막 이벤트, 보류 이유와 키 안내를 표시합니다. ACTIVE는 ON 상태에서 구간 확보 시간이 지났다는 뜻이며 품질 통과를 보증하지 않습니다. 보류 이유도 함께 확인하세요.

직접 실행 후 다음 순서로 확인하세요.

1. OFF에서 손을 움직여도 실행 로그가 없는지 확인합니다.
2. 카메라 창을 선택하고 S를 누릅니다. 오른손 하나만 보이게 하여 WARMUP과 Right detected를 확인합니다.
3. 정지/일상적인 손 움직임에서 오작동 로그가 있는지 확인합니다.
4. swipe_left와 make_fist를 각각 수행하고 한 동작당 로그가 한 번만 나오는지 확인합니다.
5. 주먹을 계속 유지해 cooldown 이후에도 반복 실행되지 않는지 확인합니다.
6. 충분히 중립 상태를 거친 뒤 다음 동작이 인식되는지 확인합니다.
7. 손을 잠깐/오래 빼거나 X를 눌러 이전 예측이 지워지는지 확인합니다. 다시 S를 눌러 새 구간으로 시작하는지도 확인합니다.
8. Esc/창 닫기로 종료한 뒤 카메라를 다시 사용할 수 있는지 확인합니다.

오작동 수, 놓친 동작, 동작당 중복 횟수, 사용자 체감 지연은 수동으로 기록하세요. 현재 구현은 이런 실시간 성능 지표를 자동 측정하지 않습니다. 원본 영상/랜드마크/예측 데이터 파일도 자동 저장하지 않습니다.

## YOLO 손모양 게이트 및 지원 범위

GUI에는 정적 손모양(YOLO) 게이트를 연결했습니다. 보자기 3초로 인식을 켜고, 주먹 3초로 끄고, 총 모양 3초로 창을 보이거나 숨깁니다. 판정은 `service/yolo_gate.py`에, GUI 연결은 `gui_runtime.py`와 `gui_widgets.py`에 있습니다. 자세한 규칙은 [GUI_README.md](GUI_README.md)를 확인하세요. **CLI(`service.main`)에는 게이트를 넣지 않았습니다.** 기존 S/X/Esc 조작과 DRY RUN 동작은 그대로입니다.

`make_fist`는 명령 클래스이고 게이트의 주먹 종료는 유지 동작입니다. 게이트가 주먹을 1초 이상 보고 있으면 `make_fist` 확정을 보류하여 종료 직전에 단축키가 나가지 않게 합니다. 3초 전에 손을 펴면 보류가 풀려 바로 실행합니다.

키보드 신호와 분류 로직은 여전히 분리되어 있으므로 다른 제어기도 `GestureController.start()`/`stop()`에 연결할 수 있습니다.

좌우 반전 없이 수집기와 같은 handedness 명칭을 사용합니다. 수집기는 시퀀스의 다수 handedness로 저장 여부를 판단하지만 서비스는 프레임별로 검사합니다. 모델 스키마와 무관하게 Right만 허용합니다. 명칭이 흔들리면 결측이나 왼손 차단으로 인한 초기화가 늘 수 있습니다. 판정은 MediaPipe handedness에 의존하므로 실제 왼손을 Right로 오인하는 상황까지 완전히 막는다는 보장은 없습니다. 이를 임의로 뒤집거나 좌표를 반전하여 해결하지 마세요.

MediaPipe는 수집기처럼 num_hands=1입니다. 양손 등장 여부를 완전히 감시하거나 같은 handedness를 가진 서로 다른 사람의 손 정체성을 유지하는 기능은 없습니다. 양손 동시/여러 사람/가림에 따른 대상 전환은 지원하지 않으므로 허용된 손 하나만 보여주세요. 화면 밖 좌표를 모델 입력에서 잘라내지 않고, 랜드마크 점 표시에만 화면 경계를 적용합니다.

잘라진 시퀀스로 학습한 모델은 슬라이딩 윈도우의 부분 동작·두 동작이 섞인 구간을 잘 분류한다고 보장할 수 없습니다. 기존 validation 100%가 실시간 정확도나 오작동 방지를 보장하지 않습니다. 필요하면 추후 구간 검출과 연속 데이터 검증을 별도 작업으로 진행해야 합니다.

## 자동 테스트

```powershell
.\.venv\Scripts\python.exe -m unittest service.test_service -v
.\.venv\Scripts\python.exe -m unittest discover -s training -p "test_*.py" -v
```

임시 합성 체크포인트/랜드마크, 모의 카메라·tracker·키 입력, 제어 가능한 시각으로 검사합니다. 실제 카메라, 사용자 키보드, 실제 validation/test 데이터는 사용하지 않습니다. 이번 구현에서는 카메라 수동 검증을 수행하지 않았으며 초기 설정과 실시간 성능도 미검증 상태입니다. 합성 테스트 통과는 서비스의 실제 제스처 분류 성능을 뜻하지 않습니다.
