# 왜 Jester 데이터셋을 쓰지 않기로 했나

> **한 줄 요약**: 공개 데이터셋 20BN-Jester로 미리 학습시킬 계획이었지만, 우리 웹캠 환경과
> 너무 달라서 도움보다 혼란이 클 것으로 판단했다. 대신 팀원 6명이 직접 녹화한 데이터만 쓴다.
> 이 문서는 발표 때 "왜 공개 데이터셋을 안 썼나요?"라는 질문에 답하기 위한 기록이다.

---

## 1. Jester가 무엇인가

20BN-Jester는 손 제스처 인식용 공개 영상 데이터셋이다.

| 항목 | 값 |
|---|---|
| 영상 수 | 약 148,000개 |
| 제스처 종류 | 27가지 (Swiping Left/Right/Up/Down, Thumb Up, Zoom In 등) |
| 영상 형식 | 각 영상이 jpg 프레임 묶음, **초당 12장**, **높이 100픽셀** |
| 우리가 쓰려던 클래스 | Swiping 4방향 각 약 4,200개 + No gesture 4,300개 + Doing other things 9,600개 |
| 용량 | 압축 파일 약 22GB |

숫자만 보면 매력적이다. 우리가 직접 900개를 찍는 것보다 수십 배 많다.

## 2. 원래 계획

계획서에는 이렇게 적혀 있었다.

1. Jester 영상에서 필요한 클래스만 꺼낸다.
2. 각 프레임에 MediaPipe를 돌려 손 21관절 좌표를 뽑는다.
3. 그 좌표 시계열로 LSTM을 **먼저 학습**시킨다 (사전학습).
4. 우리가 찍은 데이터로 **한 번 더 학습**시켜 우리 환경에 맞춘다 (파인튜닝).

말하자면 "남의 데이터로 기초를 다지고 우리 데이터로 마무리한다"는 전략이었다.
이를 위해 tar 스트리밍 추출, 프레임→좌표 변환, 우리 규약(npz)으로 저장하는 스크립트까지 만들었다.

## 3. 그런데 왜 뺐나

문제는 다섯 가지다. 하나하나가 치명적인 건 아니지만, 다 합치면 "들이는 노력 대비 얻는 게 없다"가 된다.

### 3-1. 화질이 너무 낮아서 손 관절을 못 잡는다

Jester 영상은 높이가 100픽셀이다. 손 하나가 화면에서 20~30픽셀 정도로 보인다.
MediaPipe는 손 21개 관절을 찍어주는 도구인데, 이 정도 크기에서는 관절 위치가 불안정하거나
아예 손을 못 찾는다. 우리 웹캠은 640×480이라 손이 100픽셀 이상으로 크게 보인다.

**비유**: 흐릿한 CCTV 화면으로 글씨 연습을 시키고, 실제 시험은 선명한 종이로 보는 셈이다.
연습 데이터의 좌표 자체가 부정확하면 그걸로 배운 모델은 잘못된 기초를 익힌다.

### 3-2. 프레임 속도가 다르다

Jester는 초당 12장, 우리 웹캠은 초당 30장이다.
같은 "왼쪽 스와이프"라도 Jester는 프레임당 손이 크게 뛰고, 우리 데이터는 부드럽게 움직인다.
전처리에서 30프레임으로 다시 맞추긴 하지만, 12장을 30장으로 늘리면 중간이 "추측"으로 채워진다.
움직임의 결이 달라서 모델이 두 데이터를 다른 제스처처럼 느낄 수 있다.

### 3-3. 좌우 방향이 반대다

우리 규약은 **거울 화면** 기준이다. 화면을 거울처럼 보여주고, 사용자가 자기 왼쪽으로
손을 움직이면 swipe_left다. Jester는 거울 처리가 없는 카메라로 찍었고 라벨은 수행자 시점이다.
그래서 Jester의 "Swiping Left"는 우리 화면 좌표에서는 오른쪽으로 움직이는 것으로 나온다.

좌우반전으로 맞출 수는 있다. 하지만 "이 데이터는 뒤집어야 하고 저 데이터는 안 뒤집는다"는
규칙이 하나 생기고, 누가 한 번 실수하면 swipe_left와 swipe_right 라벨이 통째로 섞인다.
6명이 데이터를 만드는 상황에서 이런 함정은 하나라도 줄이는 게 낫다.

### 3-4. 누가 찍었는지 몰라서 제대로 평가할 수 없다

우리 평가 규약은 **사람 단위 분할**이다. 예를 들어 태순 데이터를 시험용으로 빼두면
학습에는 태순 데이터가 한 장도 들어가지 않는다. 이렇게 해야 "처음 보는 사람도 인식되나?"를
정직하게 측정할 수 있다.

Jester에는 사람 ID가 없다. 같은 사람의 영상이 학습과 시험에 동시에 들어갈 수 있고,
그러면 점수가 실제보다 높게 나온다. Jester를 학습에만 넣는다 해도, 결국 우리가 믿을 수 있는
숫자는 우리 데이터로 잰 것뿐이다. 그럼 Jester로 얻는 건 "학습 데이터가 늘었다"는 것 하나인데,
3-1과 3-2 때문에 그 데이터의 품질을 믿기 어렵다.

### 3-5. 시간이 없다

프로젝트는 금요일 킥오프, 월요일 발표다. Jester를 쓰려면 22GB를 받고, 필요한 클래스만
스트리밍으로 꺼내고, 2만 개 영상에 MediaPipe를 돌려야 한다. 영상 하나에 프레임 37장,
프레임당 MediaPipe 수십 ms면 CPU로 몇 시간 단위 작업이다. 그 시간에 팀원 6명이 카메라 앞에
30분씩 앉으면 우리 환경에 딱 맞는 데이터 900개가 나온다.

## 4. 그래서 어떻게 하나

**팀원 6명이 직접 녹화한다.** 자세한 규약은 `team_conventions.md`에 있다.

| 항목 | 값 |
|---|---|
| 1인당 | 5클래스 × 30개 = 150개 (약 30~40분) |
| 전체 | 900개 |
| 평가 | 1명 시험용, 1명 검증용으로 빼고 4명분으로 학습 |
| 증강 후 학습 데이터 | 약 4,800개 (스케일·이동·시간왜곡·노이즈·좌우반전) |

이 규모는 2층 LSTM/GRU를 학습시키기에 충분하다. 6명이 각자 다른 노트북·조명·배경에서
찍기 때문에 그 자체가 다양성이 된다.

무엇보다 **학습 데이터와 실제 사용 환경이 같다.** 발표 데모에서 쓰는 카메라, 거리, 조명이
학습 데이터와 같은 조건이므로 "학습에선 잘 됐는데 데모에서 안 된다"는 위험이 가장 낮다.

## 5. Jester가 다시 필요해지는 경우

아래 상황이 오면 재검토할 가치가 있다.

- 제스처 종류를 크게 늘릴 때 (Zoom, Thumb Up 등 우리가 찍기 힘든 양)
- 우리 데이터로 학습한 모델이 새로운 사람에게 유독 약할 때
- MediaPipe가 아니라 영상을 직접 넣는 3D CNN 계열로 바꿀 때 (그때는 화질 문제가 덜하다)

## 6. 지웠던 코드 되살리기

Jester 처리 스크립트 3개와 클래스 목록은 git 히스토리에 남아 있다.

```bash
# 커밋 5fab0fc 시점의 파일을 다시 꺼낸다
git checkout 5fab0fc -- scripts/jester_stream_extract.py scripts/jester_pilot_landmarks.py scripts/jester_to_recordings.py data/jester
```

- `jester_stream_extract.py`: 22GB 분할 tar를 풀지 않고 필요한 클래스만 꺼내기
- `jester_pilot_landmarks.py`: 업스케일 배율별 MediaPipe 검출률 측정 (3-1 검증용)
- `jester_to_recordings.py`: 프레임 → 좌표 → 우리 npz 규약 변환 (좌우반전 포함)
