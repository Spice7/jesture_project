# Windows 제스처 GUI · 첫 버전

흰색·파란색의 둥근 카드 UI에 카메라 미리보기, 전역 인식 제어, 트레이, 조합키 설정, 우측 하단 알림을 연결했습니다. 기존 `service.main` CLI는 여전히 **DRY RUN**이며, 새 `service.gui`는 사용자가 인식을 ON으로 바꾸면 **현재 활성화된 외부 앱으로 실제 키 입력을 전송**합니다.

## 구현과 검증 상태

이번 작업에서는 실제 카메라, 실제 키 전송, 실제 전역 단축키 등록을 실행하지 않았습니다. 원본 NPZ/기존 결과/모델 가중치/학습 설정을 변경하지 않았고, 모델 학습·실제 데이터 평가·exe 패키징도 하지 않았습니다.

최초 구현 시 프로젝트 `.venv`에는 PySide6가 없어 GUI 테스트를 건너뛰었습니다. 이후 사용자가 설치한 환경에서 모의 트레이/메뉴 구성, 기본 모델 선택과 오른손 전용 정책을 검증했습니다. 실제 화면 배치, Windows 초점 유지와 실제 트레이/키 전송은 자동 테스트가 보증하지 않습니다. 테스트는 fake 카메라/모델/입력 API와 임시 설정 파일만 사용하며 실제 인식 정확도나 OS 입력 성공을 보증하지 않습니다. 미설치 환경에서는 GUI 테스트가 계속 명시적으로 skip됩니다.

## 설치와 실행

프로젝트 루트 PowerShell에서 실행하세요. 기존 환경/의존성 버전은 그대로 두고 GUI 패키지만 사용자가 추가합니다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r .\service\requirements-gui.txt
```

추가 패키지는 `PySide6>=6.8,<7` 하나이며 그 Qt 의존 패키지가 함께 설치됩니다. 키보드 기능은 Python 표준 `ctypes`와 Windows API를 사용하여 별도 키보드 패키지가 필요 없습니다. 설치 명령은 이번 작업에서 실행하지 않았습니다. `requirements-gui.txt`는 기존 pyproject/uv.lock에 반영되지 않은 추가 설치 목록입니다. 이후 `uv sync`로 환경을 원래 잠금 목록에 맞췄다면 GUI 의존성을 다시 확인하세요.

설치 후 **실제 장치를 사용하지 않는 테스트부터** 실행하세요.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s service -p "test_*.py" -v
.\.venv\Scripts\python.exe -m unittest discover -s training -p "test_*.py" -v
```

GUI 기본 모델은 `artifacts/four_class_lstm_1layers_001/best_model.pt`(오른손 4클래스)입니다. 모델 선택 우선순위는 `--checkpoint` → 저장된 `model_path` → 기본 모델이며, 기본 경로는 저장소 위치를 기준으로 찾습니다(exe에서는 번들 안). 이 기본 설정은 모델의 최종 성능 평가를 의미하지 않습니다.

```powershell
.\.venv\Scripts\python.exe -m service.gui --device auto
```

GUI 옵션:

- `--checkpoint`: 이번 실행에 사용할 모델. 생략하면 저장된 `model_path`, 저장값도 비어 있으면 기본 2층 모델 사용.
- `--device auto|cpu|cuda`: 기존 predictor의 장치 선택 규칙. 기본 auto.
- `--settings`: 사용자 설정 경로 재정의. 테스트/별도 설정에 사용.

```powershell
.\.venv\Scripts\python.exe -m service.gui --help
```

설정에서 외부 모델을 선택하여 저장한 뒤 앱을 재시작하세요. 기본 모델로 돌아가려면 모델 경로를 비워 저장하고 `--checkpoint` 없이 실행합니다. 명시한 모델 파일이 없거나 잘못되었을 때 다른 모델로 몰래 대체하지 않고 기존 predictor가 오류를 표시합니다. MediaPipe의 `models/hand_landmarker.task`와 기존 `training/` 의존 코드가 필요하며, 학습 데이터 파일은 필요하지 않습니다.

기존 CLI 실행은 변경하지 않았습니다. CLI에는 손모양 게이트가 없고 `--checkpoint`가 필수입니다.

```powershell
.\.venv\Scripts\python.exe -m service.main --checkpoint .\artifacts\four_class_lstm_1layers_001\best_model.pt --device auto
```

## 실행 파일로 배포하기

파이썬 없이 쓸 수 있는 `Jesture.exe`를 만들 수 있습니다. 빌드 방법과 제약은 [packaging/README.md](../packaging/README.md)에 있습니다. 배포본은 CPU 전용이며 GUI 서비스만 담습니다. 학습과 데이터 수집은 저장소에서 그대로 실행하세요.

## 손모양 게이트 (YOLO)

앱을 켜면 카메라가 바로 열리고 정적 손모양 모델이 계속 화면을 봅니다. 손모양 하나를 **3초 유지**하면 동작이 한 번 확정됩니다.

| 손모양 | 모델 라벨 | 동작 |
| --- | --- | --- |
| 보자기 | `start` | 제스처 인식(MediaPipe + LSTM)을 켭니다 |
| 주먹 | `stop` | 제스처 인식을 끕니다. 카메라와 게이트는 그대로 돕니다 |
| 총 모양 | `cancel` | 메인 창을 보이거나 숨깁니다 |

기본 가중치는 `yolo/v2/best.pt`이며 `--gate-weights`로 바꾸거나 `--no-gate`로 끌 수 있습니다. 가중치를 읽지 못해도 서비스는 계속 동작하며 버튼과 전역 단축키로 인식을 켤 수 있습니다.

확정 규칙은 기존 명령 판정과 같은 취지입니다. 같은 손모양이 끊기지 않고 이어져야 하며, 0.4초 이상 놓치거나 다른 손모양으로 바뀌면 처음부터 다시 셉니다. 한 번 확정한 뒤에는 **그 손모양을 놓기 전까지 다시 확정하지 않습니다.** 계속 유지한다고 반복 실행되지 않습니다.

창을 띄울 때는 **활성 창을 바꾸지 않습니다.** 본 앱이 활성 창이면 `KeySender`가 단축키 전송을 막기 때문입니다. 창을 보면서도 제스처 명령은 계속 대상 앱으로 나갑니다. 트레이 아이콘으로 여는 경우에는 사용자의 명시적 조작이므로 기존대로 창을 활성화합니다.

### 주먹과 `make_fist` 명령의 관계

`make_fist`는 편 손에서 주먹으로 **변하는 과정**이고, 게이트의 `stop`은 주먹을 **유지**하는 상태입니다. 두 판정이 겹치지 않도록, 게이트가 주먹을 1초 이상 연속으로 보고 있으면 `make_fist` 확정을 보류합니다.

- 3초를 채우면 단축키 없이 인식만 끕니다.
- 3초 전에 손을 펴면 보류가 풀려 바로 다음 추론에서 `make_fist`를 실행합니다.

따라서 `make_fist` 명령에 최대 1초 정도 지연이 생길 수 있습니다. 이 값들은 초기 실험값이며 `yolo_gate.GateConfig`에 있습니다.

## 상태와 카메라 동작

- 앱 실행: 모델을 작업자에서 로딩한 뒤 **카메라를 열고 손모양 게이트를 시작**합니다. 제스처 인식 자체는 **OFF**로 시작하며 이전 ON 상태를 저장/복원하지 않습니다.
- 인식 시작: 보자기 3초, 버튼, 전역 단축키 중 무엇으로든 켜집니다. 새 시퀀스부터 WARMUP을 진행합니다.
- 미리보기 숨김: 영상 표시/GUI용 프레임 복사만 생략합니다. 카메라, 게이트, 추적, 추론, 단축키 처리는 계속됩니다.
- 인식 중지: 즉시 명령 권한을 취소하고 버퍼와 추적 상태를 비웁니다. **카메라와 게이트는 계속 돌아가므로** 화면에는 `인식 OFF · 카메라 사용 중`이 남습니다. 보자기로 다시 켤 수 있어야 하기 때문입니다.
- 카메라 번호 변경: 설정에서 저장하면 작업자가 카메라를 다시 엽니다.
- 카메라 오류: 인식을 끄고 오류를 표시합니다. 같은 오류로 무한 재시도하지 않으며, 설정에서 카메라 번호를 저장하면 다시 시도합니다.
- 재시작: 이전 구간과 명령을 이어 쓰지 않습니다.
- 최소화: 시스템 트레이가 있으면 메인 창을 숨기고 계속 작동합니다. 트레이를 사용할 수 없으면 일반 최소화로 남겨 사용자가 창을 잃지 않게 합니다.
- 창 X / 트레이 종료: 실제 종료. 키 등록과 본 프로그램의 미해제 키를 정리하고 작업자 종료를 기다립니다.

네이티브 카메라 읽기나 모델 로딩 호출이 장시간 멈추면 그 호출이 돌아올 때까지 자원 정리/종료가 지연될 수 있습니다. 다른 스레드에서 강제 해제하거나 작업자를 강제 종료하지 않습니다. 이때도 명령 전송 권한은 이미 OFF입니다. 첫 버전은 카메라 드라이버의 무기한 대기를 강제로 복구하는 기능을 제공하지 않습니다.

## 모델과 지원 라벨

기존 체크포인트의 model_config/label_map/preprocessing_config를 검증하고 재사용합니다. 분류기/전처리/임계값은 바꾸지 않았습니다.

| 라벨 | 화면 표시 | 동작 | 기본 키 |
| --- | --- | --- | --- |
| swipe_left | 왼쪽으로 스와이프 | 오른손으로 화면 왼쪽 이동 | Left 방향키 |
| make_fist | 손 오므리기 | 오른손으로 손 펴기 → 주먹 | Space |
| no_gesture | 표시하지 않음 | 오른손 중립, 비명령 | 없음, 설정 불가 |
| finger_snap | 핑거 스냅 | 오른손 손가락 튕기기 | 미지정, 옵션 창에서 지정 |

서비스는 **오른손 전용**이며 새 4클래스와 기존 3클래스 모델을 구분합니다. finger_snap은 네 번째 출력이 있는 모델에서만 설정 버튼이 활성화됩니다. 기본 단축키는 미지정(null)이므로 인식되더라도 키를 전송하지 않고 상태만 표시합니다. 옵션 창에서 키를 지정하고 저장한 후 사용하세요. no_gesture는 명령으로 실행하지 않습니다. 좌우 반전 증강과 왼손 모델은 지원하지 않습니다. 과거 설정 파일의 폐기된 단축키 항목은 읽을 때 제외하며, 나머지 사용자 설정은 유지합니다. 로딩만으로 설정 파일을 덮어쓰지 않으며 다음 저장 시 정리됩니다.

### 화면 문구 (`ui_text.py`)

GUI에 보이는 문구는 `service/ui_text.py`의 표시 계층에서만 한국어로 바꿉니다. 라벨 계약, 판정 로직, 설정 파일의 키, 진단 로그(`--diagnostics`)와 CLI(`service.main`)의 영어 문자열은 그대로 두므로 기존 로그 분석과 테스트는 영향을 받지 않습니다.

| 위치 | 내용 |
| --- | --- |
| 모델 줄 | `모델: 오른손 전용 · 왼쪽으로 스와이프, 손 오므리기, 핑거 스냅`. 명령이 아닌 no_gesture는 목록에서 뺍니다. 모델 로딩 전에는 `모델: 로딩 전`입니다. |
| 손모양 게이트 줄 | `손모양 게이트: 보자기 0.93 · 유지 66%`. 손모양이 없으면 `손모양 대기 중 · 보자기=시작, 주먹=중지, 총 모양=창 표시`입니다. start/stop/cancel 같은 모델 라벨은 노출하지 않습니다. |
| 미리보기 아래 | `손 상태 · 보류 사유`를 각각 사용자 문장으로 바꿉니다. 예: `오른손을 감지했습니다 · 동작을 한 번 더 확인하고 있습니다`. 두 쪽이 같은 안내면 한 번만 표시합니다. |
| 마지막 명령 | `마지막 명령: 핑거 스냅 · 단축키 미지정 · 키 전송 없음`처럼 한국어 이름으로 표시합니다. |
| 단축키 설정 | 라벨 버튼도 같은 한국어 이름을 사용합니다. |

`Quality hold:`의 원인 토큰과 `Expected Right, got …`의 손 이름은 사용자에게 노출하지 않고 할 일만 안내합니다. 번역표에 없는 새 문구는 `상태를 확인하고 있습니다`로 표시됩니다. `service/test_ui_text.py`가 `gesture_controller.py`·`hand_tracker.py`의 고정 문구를 AST로 수집해 번역 누락을 검사하므로, 새 보류 사유를 추가하면 `STATUS_NAMES`에도 함께 넣어야 테스트를 통과합니다.

Left로 판정된 프레임은 추론에 넣지 않고 기존 시퀀스를 초기화합니다. 오른손으로 돌아오면 새 구간과 중립 확인이 필요합니다. 두 손 동시는 지원하지 않습니다. MediaPipe의 손 구분 오판정까지 완전히 차단한다고 보장할 수는 없습니다.

모델은 작업자에서 한 번 로딩합니다. 호환되는 외부 `best_model.pt`로 교체한 뒤 앱을 재시작하세요. 실행 중 hot reload는 없습니다. 설정에서 바꾼 모델 경로도 다음 실행부터 적용됩니다. `--checkpoint`를 지정하면 저장 경로보다 우선하므로 저장된 경로를 사용하려면 다음 실행에서는 해당 옵션을 생략하세요. 모델 교체 시 단축키 설정은 유지됩니다.

## 전역 제어와 대상 앱

### Windows 키 조합 지정

제스처 실행용으로 **Win+D**, **Win+Shift+S**를 허용합니다. 라벨 선택 → Windows 키 포함 체크 → D 또는 Shift+S 입력 → 저장 순서로 설정하세요. Win+Shift+S는 수정키 정렬 규칙에 따라 화면에 Shift+Win+S로 표시될 수 있으며 같은 조합입니다. 두 조합은 전역 시작/중지용으로는 지정할 수 없습니다. 그 외 예약 조합 제한과 대상 창·물리 키 상태 검사는 유지합니다.

단축키 옵션에서 라벨을 선택하고 **Windows 키 포함 (Win)**을 체크한 뒤 일반 키 하나를 입력하세요. 예를 들어 체크 후 F2를 누르면 Win+F2로 저장됩니다. Ctrl/Alt/Shift를 함께 누르는 것도 가능합니다. 체크 상태를 바꾸면 일반 키를 다시 입력해야 저장할 수 있습니다. 체크를 해제하면 Win을 자동으로 추가하지 않습니다.

실제 Win 키를 누르는 입력도 지원하지만 Windows가 먼저 조합을 처리할 수 있어 체크박스 사용을 권장합니다. 체크박스는 키 조합 설정만 하며 실제 OS 키를 누르거나 시스템 단축키를 가로채지 않습니다. Win 단독, Win+L, Win+방향키 등 현재 정책상 예약 조합은 계속 차단합니다. 전역 시작/중지로 지정할 경우 Windows 등록 실패가 발생할 수 있으며, 모든 Win 조합의 동작을 보장하지 않습니다.

기본 **Ctrl+Alt+G**로 인식을 시작/중지합니다. 메인 창 버튼과 트레이 메뉴로도 제어할 수 있습니다. GUI에서 S/X 같은 일반 문자를 전역으로 가로채지 않습니다.

전역 조합은 `RegisterHotKey`와 `MOD_NOREPEAT`를 사용합니다. 길게 누른 반복 신호로 여러 번 토글되지 않게 하며, 등록 충돌은 UI에 오류로 표시합니다. 등록에 실패해도 메인 버튼과 트레이로 인식을 중지할 수 있습니다. 전역 제어 기능을 원하면 설정에서 다른 조합을 지정하세요. [Microsoft RegisterHotKey 문서](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)

명령은 추론 당시의 외부 활성 창과 전송 직전의 창/PID가 일치할 때만 전송합니다. 본 앱이 활성화되어 있거나, 대상이 불명확하거나, 사용자 수정키/전송 대상 키가 이미 눌려 있으면 **건너뛰고 재시도하지 않습니다**. 활성 앱이 바뀐 프레임에서는 기존 구간을 초기화하고 중립을 다시 요구합니다. 사용자 입력을 기록하는 전역 키보드 훅은 없습니다.

마지막 검사 직후 사용자가 창을 바꾸거나 키를 누르는 OS 수준의 경쟁까지 원자적으로 차단할 수는 없습니다. Windows 권한 차이(UIPI), 보안 데스크톱, 대상 앱 정책 등으로 입력이 제한될 수 있습니다. 관리자 권한을 강제하지 않습니다. 첫 버전은 비관리자 권한의 일반 데스크톱 앱에서 점검하세요. [Microsoft SendInput 문서](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

## 단축키 설정과 저장

`단축키 · 설정`을 열면 인식이 OFF가 됩니다. 전역 토글 등록도 잠시 해제하여 설정 입력을 가로채지 않게 합니다. 저장/취소 뒤 전역 등록을 복원하지만 **인식은 자동으로 다시 켜지지 않습니다**.

1. 변경할 라벨 또는 전역 토글 버튼을 클릭합니다.
2. 입력란에서 키를 누릅니다. Ctrl을 누른 채 C를 누르면 `Ctrl+C`입니다.
3. 잘못 입력하면 다시 입력합니다. Esc는 해당 입력을 취소합니다.
4. 저장을 눌러 설정을 확정합니다. 저장 성공 후 창이 닫힙니다.
5. 취소/X는 draft를 버립니다. 기본값 복원도 저장 전에는 실제 설정을 바꾸지 않습니다.

지원 키는 영문 A~Z, 숫자 0~9, F1~F11, 방향키, Space/Enter/Tab/Backspace/Delete/Insert/Home/End/PageUp/PageDown입니다. 수정키 Ctrl/Alt/Shift/Win + 일반 키 하나의 조합을 지원합니다. 일반 키 여러 개를 동시에 누르거나 시간차 매크로를 저장하는 기능은 없습니다. 수정키만 저장할 수 없으며 전역 제어에는 수정키가 필수입니다.

Esc는 취소 전용, F12는 예약 키로 제외합니다. Win+L/Win+D, Alt+Tab, Alt+F4, Ctrl+Alt+Delete 등 명백한 시스템 조합도 거부합니다. Win 조합 일부는 허용하지만 모든 OS/외부 앱 예약 키를 검사하거나 차단할 수는 없습니다. 특히 OS 예약 조합은 설정 입력 중에도 OS가 먼저 처리할 수 있으므로 누르지 마세요.

제스처 단축키와 전역 토글이 동일하면 저장을 거부합니다. 서로 다른 제스처에 같은 기능을 연결하는 것은 허용합니다. 전역 등록 실패 시 창을 열어 오류를 표시하며, 설정 저장 실패 시 기존 파일과 설정을 유지하고 등록을 복원합니다. 등록 복원도 실패했다면 전역 제어 오류가 표시되므로 버튼으로 중지하고 설정을 다시 확인하세요.

입력 전송은 수정키 누름 → 일반 키 누름/해제 → 수정키 역순 해제입니다. 일부 전송 실패 시 API가 성공했다고 보고한 본 프로그램의 키만 정리하고 인식을 중지합니다. 명령은 자동 재시도하지 않습니다. 사용자와 프로그램이 같은 키를 정확히 동시에 조작하는 경우의 물리적 소유권까지 완전히 구분하지는 못합니다.

## 알림

기본 모니터의 작업 영역 우측 하단에 약 2.3초 동안 작은 알림을 표시합니다. 알림 하나를 재사용하므로 계속 쌓이지 않습니다. Qt의 비활성화/입력 통과 창 플래그를 지정하고 `activateWindow()`를 호출하지 않습니다. 실제 Windows 초점 유지 여부는 수동 확인이 필요합니다.

- 인식 시작/중지
- `swipe_left · Left 입력 전송` 같은 실제 전송 결과
- 입력 실패/카메라/모델 오류는 메인 화면에 표시하고 인식을 중지

알림 OFF는 일반 팝업만 끕니다. 현재 상태/오류 표시는 유지합니다. 입력 전송 성공은 대상 앱의 실제 기능 수행 성공을 뜻하지 않습니다. 앱 종료 때는 팝업 표시를 위해 프로세스를 유지하지 않고 자원 정리를 우선합니다.

## 설정 파일과 복구

기본 위치: `%LOCALAPPDATA%\JestureService\settings.json`

라벨별 키, 전역 토글, 알림/미리보기, 카메라 번호, 모델 경로와 설정 버전 1을 저장합니다. 최초 실행에서 파일을 자동 생성하지 않고 사용자가 설정을 저장할 때 생성합니다. 임시 파일 작성 후 교체하며, 저장 실패 시 이전 파일을 보존합니다. 원본 NPZ/모델/저장소에는 사용자 설정을 쓰지 않습니다.

필드 일부 누락은 기본값으로 보충하지만 잘못된 키/자료형/버전/중복 JSON 키는 거부합니다. 손상된 설정은 **덮어쓰지 않고 저장을 차단**하며 메모리 기본값으로만 화면을 열 수 있습니다. 앱을 종료하고 해당 파일을 별도 이름으로 옮겨 보관한 뒤 재실행하세요. 파일은 자동 삭제하지 않습니다. 다른 프로그램/다른 실행 인스턴스가 설정을 변경한 경우에도 덮어쓰지 않고 재실행을 요구합니다. 동시에 앱 여러 개를 실행하는 사용은 권장하지 않습니다.

## 사용자가 직접 확인할 순서

실제 카메라와 전역 입력 테스트는 아래 순서로 사용자가 진행합니다. 먼저 중요한 문서나 저장되지 않은 작업을 닫고 **저장할 필요 없는 테스트 문서/무해한 앱**을 사용하세요.

1. GUI 모의 테스트를 실행합니다. skip이면 해당 기능 검증이 끝난 것이 아닙니다.
2. GUI를 실행하고 OFF·카메라 해제 상태인지, 현재 모델/지원 라벨이 맞는지 확인합니다.
3. 설정에서 기본 키, 조합키, 취소/기본값 복원/저장 및 재실행 후 유지 여부를 확인합니다.
4. 다른 앱으로 전환한 뒤 Ctrl+Alt+G로 시작/중지가 가능한지 확인합니다. 등록 오류가 있으면 다른 조합을 선택합니다.
5. 안전한 테스트 창에서 한 제스처가 키 한 번만 전송하는지, 중립 복귀가 필요한지 확인합니다.
6. 미리보기만 숨긴 뒤에도 상태 표시/인식이 유지되는지 확인합니다.
7. 알림이 우측 하단에 나타나도 타이핑 대상과 활성 창이 바뀌지 않는지 확인합니다. 알림 OFF도 확인합니다.
8. 우리 앱/설정 창이 활성화되어 있으면 제스처가 UI를 조작하지 않는지 확인합니다. 설정을 닫아도 OFF인지 확인합니다.
9. 최소화해 트레이로 보낸 뒤 인식/중지/창 복원이 가능한지 확인합니다.
10. X와 트레이 종료를 각각 확인하고, 이후 카메라와 전역 조합을 다른 프로그램에서 사용할 수 있는지 확인합니다.

왼손을 보여주면 명령이 실행되지 않고 오른손으로 돌아온 뒤 새 구간/중립을 요구하는지도 확인하세요. CPU/GPU의 실제 처리 지연, 화면 배율, 다중 모니터, Windows 키보드 레이아웃, 대상 앱별 입력 동작도 배포 전에 확인해야 합니다. exe/다른 PC 배포 검증은 아직 수행하지 않았습니다.

## 인식 지연 진단 (선택 사항)

지연 비교용 기본 설정: 명령 확정 2회, 중립 복귀 2회입니다(기존 각각 3회). 시간 창 1.5초, 추론 간격 0.15초, 신뢰도 0.8, 쿨다운 1초와 창 변경 시 초기화는 유지합니다. 빠른 응답이 실제로 개선되는지와 오작동·중복 실행이 늘지 않는지를 새 로그로 비교하세요. 과거 로그의 session_start.config는 당시의 3회 설정을 그대로 기록합니다.

기존 명령에 `--diagnostics .\gesture_timing_001.jsonl`을 붙여 실행합니다. 이 옵션이 없으면 진단 파일/저장 스레드를 만들지 않습니다. 기존 로그는 덮어쓰지 않으므로 재실행할 때 파일 번호를 바꾸세요. 인식 창·임계값·안정화·중립 복귀 조건은 변경하지 않습니다.

```powershell
.\.venv\Scripts\python.exe -m service.gui --device auto --diagnostics .\gesture_timing_001.jsonl
```

앱을 완전히 종료한 뒤 JSONL을 확인합니다. 한 줄이 이벤트 하나이며 UTC 시간, monotonic_s(단조 증가 시계), elapsed_s(실행 시작 기준 초)를 포함합니다. 별도 PowerShell에서 `Get-Content .\gesture_timing_001.jsonl -Wait`로 확인할 수도 있습니다.

- prediction: 매 추론의 label/confidence/전체 probabilities, inference_ms(전처리+LSTM+결과 반환 시간), frame_s(카메라 읽기 완료 후 시각), 실제 창 길이·프레임 수, 연속 횟수 candidate_count/stable_required, neutral_count/neutral_required, armed, cooldown_remaining_s, reason을 기록합니다.
- state: 워밍업·손 검출 실패·중립 대기 등 상태 변화. prediction이 없다면 창이 채워지지 않았거나 손 입력이 유효하지 않은 상태부터 확인합니다.
- confirmed: 컨트롤러 명령 확정. 실제 키가 전송됐다는 뜻은 아닙니다.
- runtime_hold / command_replaced: 입력 지연·대상 창 변경이나 GUI 최신 슬롯 교체로 결과를 보류/폐기한 경우.
- command_queued → gui_command → key_send_start → key_send_result: session/serial로 연결합니다. confirmed와는 session/frame_s로 연결합니다. gui_command.accepted=false는 세션·만료·라벨 등의 최종 검사에서 거부된 경우입니다. sent=false면 reason에서 물리 키 눌림·미지정·대상 창 변경 등을 확인합니다. sent=true는 SendInput 접수 성공이지 대상 앱의 동작 완료 시각이 아닙니다.

같은 클래스의 첫 prediction과 confirmed를 비교하면 안정화에서 추가된 지연을 볼 수 있습니다. 낮은 확률이나 다른 클래스가 섞이면 연속 횟수가 초기화됩니다. 이 로그는 정답 라벨이나 실제 손동작 종료 시각을 자동으로 알지 못합니다. 별도로 녹화한 화면과 UTC 시각을 맞춰 **동작 종료 → 첫 정답 예측 → 명령 확정 → 키 전송**을 비교하세요. 화면 녹화는 이 기능에서 수행하지 않습니다.

영상·랜드마크 좌표·활성 창 이름·사용자 키 입력 내용은 저장하지 않습니다. 로그에는 클래스와 실행 시간 등 사용 패턴이 남을 수 있으므로 공유 전 확인하세요. 저장은 별도 스레드와 최대 4096개 큐를 사용하고, 큐가 가득 차면 로그를 누락시켜 인식을 막지 않습니다. 정상 종료의 diagnostics_closed.dropped가 0보다 크면 로그만으로 전체 흐름을 확정하지 마세요. 파일은 약 20MB에서 저장을 중단하고 터미널에 알립니다. 로그 자체의 부하가 완전히 0인 것은 아닙니다.
